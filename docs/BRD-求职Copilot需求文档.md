## 1. 背景与机会

- 本人 2028 届 Java 后端 + Agent 方向，**2027-03~05 暑期实习投递是最关键窗口**，求职准备是未来 5 个月（至 2027-03 投递启动）的主旋律。
- 当前求职流程的真实痛点（本人即用户）：
  1. JD 散落在各平台，分析靠肉眼逐条比对；
  2. 简历与岗位的匹配度、差距清单全凭感觉；
  3. 面试准备低效——八股与项目细节复习没有优先级，不知道该补哪；
  4. 投递进度散落在 Excel / 聊天记录，复盘无从谈起。
- 市面 AI 工具竞品扫描：

  | 工具类型 | 代表 | 它们做了什么 | JobPilot 差异点 |
  |---|---|---|---|
  | AI 简历优化 | 超级简历、Kickresume | 单点"帮你写/改简历" | 全流程闭环 + 个人知识库 |
  | 面试模拟 | Pramp、Interviewing.io | 真人对练 / 固定题库 | 基于**自己项目经历**的 Agent 追问 |
  | 知识管理+AI | Notion AI、Obsidian Copilot | 通用文档问答 | 求职领域定制切分/检索/引用策略 |
  | 投递追踪 | 各类 Excel 模板 | 手动表格记录 | 对话式记录 + 自动统计 + Agent 复盘 |

- 双重目标：**产品价值**（自用提效）+ **能力证明**（Java 21 + AI Agent 工程能力，2027-03 面试可现场演示；叙事主线：PaiCLI 通用引擎 → JobPilot 领域落地，「一次内核、两次落地」）。

## 2. 目标用户

- **主要用户：本人**（dogfooding，2027 春招真实使用）。
- 「同届同学使用」属未验证假设：**不做登录壳（降 P2 预留）**，仅要求数据模型 day1 带 user_id 字段作防返工保险。

## 3. 产品目标（北极星）

> 一句话：把「JD → 匹配 → 准备 → 投递 → 复盘」全流程，装进一个带个人求职知识库的 Agent 对话台。

- 北极星指标：**2027-03 投递启动后，投递期内每周真实使用 ≥ 4 天**（02 月为模拟投递演练期，真实验证数据 03 月回填）。

## 4. 核心场景（用户故事）

| ID | 场景 | 级别 | 描述 | 验收条件 |
|---|---|---|---|---|
| US-1 | 知识库问答 | P0 | 导入 JD/面经/八股/项目文档后提问，回答**引用溯源**到具体文档段落 | ① 支持 md/txt/PDF 导入；② 回答附带 [文档名 > 段落] 格式引用；③ 无相关内容时明确告知而非编造 |
| US-2 | JD 分析 | P0 | 粘贴 JD → Agent 解析技术栈/要求/疑点 → 结合本人简历给匹配度与差距清单 | ① 输出结构化（技术栈/经验要求/疑点三段）；② 差距项可追溯到简历原文；③ 支持单 JD 对比 |
| US-3 | 面试模拟官 | P0 | 选岗位与范围 → Agent 多轮追问（基于我的项目细节深挖）→ 评估报告 + 弱点清单写入长期记忆 | ① 至少 3 轮递进追问（基础→深挖→压力）；② 追问引用知识库中项目文档；③ 结束后生成弱点摘要并写入记忆 |
| US-4 | 投递进度管理 | P1 | 对话式记录/查询/统计投递状态（看板视图移 P2） | ① 自然语言记录投递（公司/岗位/状态/日期）；② 按状态/时间查询；③ 简单统计（总数/各状态数）；④ 看板视图 P2 |
| US-5 | 简历要点生成 | P1 | 基于 JD 与个人经历生成要点草稿，**HITL：AI 生成 → 人工确认后才入库** | ① 输入 JD + 选择目标经历；② 输出 3~5 条定制化要点；③ 用户逐条确认/编辑后才写入；④ 拒绝的草稿不持久化 |

## 5. 功能范围（P0/P1/P2 分级，保护关键路径）

| 级别 | 范围 | 说明 |
|---|---|---|
| **P0（AI 闭环）** | **FP-1** 文档导入 → 切块 → 本地嵌入 → Chroma → 检索问答 + 引用；**FP-2** 最小同步 Agent（自研 ReAct runner + `knowledge_search` / JD 分析工具）；**FP-3** 基础 trace + 一个 HITL 审批场景；**FP-5** 基础模型配置 | 这是简历项目的最低可展示闭环；优先保证能跑、能测、能讲清 |
| **P1（增强能力）** | **FP-4** 基础长期记忆；投递 CRUD 工具；Spring AI 接入（若能降低供应商适配成本）；同步 API 稳定性优化 | 只在 P0 稳定后实现，不让框架迁移阻塞核心闭环 |
| **P2（产品壳/扩展）** | SSE、对话页、知识库管理页、JWT、多模型路由、完整投递体验、复杂记忆治理 | 时间紧张时全部后置；保留为演示增强项 |

### 5.1 P0 实现依赖顺序

```
FP-1 RAG Pipeline（可独立开发，M1 交付）
  └─► FP-2 Agent 对话 + 知识库检索工具（依赖 FP-1 提供检索接口）
        └─► FP-3 横切点 trace / HITL（叠加在 FP-2 的 Agent 循环上）
              └─► FP-4 长期记忆（依赖 FP-2 工具注册机制 + FP-3 审批门控）
FP-5 LLM 配置（贯穿，无前置依赖，day1 即可用）
```

> M1 只交付 FP-1；M2 按 FP-2 → FP-3 → FP-4 顺序递进，FP-5 随 FP-2 一起完成。

## 6. 非目标（明确不做）

- ❌ 简历复杂排版 / PDF 渲染（已有简历工具链）；
- ❌ **PDF 表格结构还原 / 扫描件 OCR**（求职材料以 md/txt 与网页复制为主，此类文件兜底 = 手动粘贴）；
- ❌ 爬虫抓取招聘平台（合规风险，JD 一律手动粘贴）；
- ❌ 通用 chatbot（一切功能围绕求职领域）；
- ❌ 高并发/高可用设计（单用户 dogfooding，别过度工程）；
- ❌ 实时协同 / 多端同步（本地单机使用）；
- ❌ 自动投递 / 平台对接（合规 + 复杂度双重不可控）。

### 7.1 评测集规范

| 维度 | 说明 |
|---|---|
| 规模 | 20 条固定 QA 对（问题 + 期望引用段落 ID） |
| 类型分布 | 事实型 8 条（某技术点定义/用法）、比较型 5 条（A vs B 优劣）、综合型 4 条（跨文档关联）、无答案型 3 条（应拒答） |
| 判定标准 | P@5 = Top5 检索结果中命中期望段落的比率高；"命中" = 引用段落与期望段落**文本重叠 ≥ 50%** 或同属一段 |
| 触发时机 | M1 交付时跑第一次；每次变更切分/嵌入/检索策略后重跑；M4 演练前终测 |

## 8. 非功能需求（NFR）

| ID | 维度 | 要求 | 说明 |
|---|---|---|---|
| NFR-1 | 响应延迟 | 用户发送 → 首 token 输出 ≤ 5s；单次 RAG 检索（含嵌入）≤ 2s | 开发期本地 Ollama + LLM API 混合，不做极端性能优化 |
| NFR-2 | LLM 成本 | 月度 LLM API 支出上限 ¥100；嵌入走本地零成本 | 开发期使用便宜模型（如 deepseek-chat），演示期可临时切强模型；Agent 对话设 max_token 上限 |
| NFR-3 | 降级策略 | Ollama 不可用 → 提示"嵌入服务离线，请检查本地服务"；LLM API 超时(>30s) → 重试 1 次后返回友好错误；Chroma 不可用 → 降级为关键词检索（MySQL 全文索引兜底） | 单用户场景，不做熔断/限流等重型方案 |
| NFR-4 | 数据安全 | MySQL 每日自动备份（mysqldump cron）；Chroma 数据目录纳入本地 git-lfs 或手动备份脚本；导入文档保留原始文件副本 | 防止本地环境损坏丢失全部知识积累 |
| NFR-5 | 容量预期 | 知识库 ≤ 500 篇文档 / ≤ 200 万字（Chroma 本地完全胜任）；单轮对话上下文窗口按模型限制管理 | 不做分布式向量库，不预留亿级数据架构 |
| NFR-6 | 可观测性 | 每次 Agent 调用记录 trace（输入/工具链/输出/耗时/token 消耗），写入 MySQL 日志表 | 支撑 debug + 面试展示"工程化意识" |

## 9. 里程碑（时间盒至 2027-03，按每周有效 8~15h 校准）

| 里程碑 | 时间 | 产出 | 缓冲/滑移策略 |
|---|---|---|---|
| M-0 | 需求与架构校准 | 技术路线、核心范围、求职优先级明确 | 不再把 LangChain4j 或 agent-kernel 写成既定前置依赖 |
| M-1 | RAG 闭环 | 导入 → 嵌入 → Chroma → 引用问答；完成评测集初跑 | 当前已完成最小 API 闭环，继续补评测集与已知技术债 |
| M-2 | Agent 最小闭环 | 自研同步 ReAct runner + `knowledge_search` + 一个 JD 分析工具 + trace + 一个 HITL | Spring AI 只在能降低协议适配成本时引入；不阻塞核心 loop |
| M-3 | 求职准备冻结 | 简历话术、项目复盘、demo 脚本、bug 修复 | 不接新产品需求 |
| M-4 | 产品壳增强 | 可选 SSE、最小前端、投递体验 | 仅在 P0/P1 后端稳定且时间充足时实现 |

> **回退准则**：若 M-2 截止（12-20）Agent 核心 loop 未跑通，触发范围重审——砍 FP-4 长期记忆至 M-4、砍 JD 解析工具至 P1，保 FP-2 基础对话 + FP-1 检索为最低可用集。

## 10. 技术基线（约束级，细化留给架构设计）

- 后端：Java 21 + Spring Boot 3.x + MyBatis-Plus + MySQL + Redis；
- AI：M-1 使用 JobPilot 自定义 Port + `RestClient` 适配 Ollama/Chroma；M-2 优先自研最小同步 ReAct runner。Spring AI 作为候选基础 AI 接入层，用于统一 Chat/Embedding/Tool Calling 等供应商协议，但不得接管 JobPilot 的预算、HITL、trace 和领域工具控制流；不引入 LangChain4j 作为当前运行时依赖；
- 嵌入：**本地 Ollama bge-m3（零 API 成本）**，与 Chroma 0.6.x REST 适配；LLM API 仅用于对话/生成；
- 向量库：**Chroma（锁定）**，本地文档量级远够用；
- 流式：SSE 后置，先完成同步闭环；
- 前端：不作为后端核心闭环前置，时间紧张时只保留 API 演示；
- 开发期模型策略：模型名称、endpoint、超时、max_iterations 配置化；Agent 循环默认 max_iterations = 5 防无限递归；
- **简历优先级**：优先交付可运行、可测试、可解释的后端闭环；不以堆砌框架数量作为技术亮点。

## 11. 核心概念模型（BRD 级，指导架构设计方向）

### 11.1 关键实体关系

```
User (1) ──── (N) Document
User (1) ──── (N) Conversation ──── (N) Message
User (1) ──── (N) Memory (长期记忆条目)
User (1) ──── (N) Application (投递记录)
Document (1) ──── (N) Chunk ──── (1:1) VectorEntry (Chroma)
Conversation (N) ──── (1) JobDescription? (可选关联)
```

| 实体 | 存储 | 说明 |
|---|---|---|
| Document | MySQL 元信息 + Chroma 向量 | 原始文件副本保留本地磁盘；切块后 Chunk 文本存 MySQL，向量存 Chroma |
| Conversation / Message | MySQL | 多轮对话记录，支持按时间/关联 JD 查询 |
| Memory | MySQL 自建表 | 用户级持久知识（见 §11.2） |
| Application | MySQL | 投递进度（公司/岗位/状态/时间/关联 JD/备注） |
| TraceLog | MySQL | Agent 调用链路日志（见 NFR-6） |

### 11.2 长期记忆 vs RAG 知识库边界

| 维度 | RAG 知识库（Document/Chunk） | 长期记忆（Memory） |
|---|---|---|
| **内容** | 外部导入文档：JD、面经、八股、项目描述 | Agent 交互中**自动/半自动沉淀**的结构化条目 |
| **粒度** | 文档级 / 段落级 | 单条知识/偏好级（如"Java 并发方面表达不自信"） |
| **生命周期** | 用户主动增删改 | Agent 面试评估后写入弱点；用户可显式删除/编辑；不自动过期 |
| **使用方式** | 检索增强——召回段落注入 prompt 作为参考依据 | 记忆注入——作为 system prompt 上下文，影响 Agent 行为策略 |
| **举例** | "Spring 事务传播机制详解" 文档段落 | "用户在分布式事务场景被追问 2 次未答好" |

> 设计原则：记忆条目 **短小、可枚举、结构化**（JSON/表格行）；知识库内容 **长文本、需向量检索**。如果一条信息 > 200 字或需要语义检索，它应该进知识库而非记忆。

### 11.3 HITL 审批流程

触发条件：Agent 产生**对外持久化副作用**时，必须经用户确认后才执行：

| 操作 | 审批粒度 | 拒绝处理 |
|---|---|---|
| US-5 简历要点写入知识库 | 逐条确认（可编辑后确认） | 丢弃该条草稿，不持久化 |
| US-3 面试弱点写入长期记忆 | 整批确认（评估报告一次性审核） | 可选择部分条目写入 |
| 知识库文档删除 | 单次确认 | 取消删除 |
| 投递记录写入/更新 | 自动执行（低风险，无需审批） | — |

> 不触发审批的操作：纯检索、对话回复、trace 日志写入、JD 解析输出（仅展示，不持久化）。

## 12. 风险与对策

| ID | 风险 | 影响 | 对策 |
|---|---|---|---|
| R-1 | 范围蔓延（做成八爪鱼） | 高 | 严格 P0/P1/P2；新想法一律先进 backlog，不进当前迭代 |
| R-2 | 期末/春节产能归零 | 高 | M-3 主动冻结，只保留文档/话术类零耗任务；M-3 两周零 commit 属预期，不触发重审 |
| R-3 | PaiCLI 叙事重叠 + commit 历史薄弱 | 中 | JobPilot 不直接复用 PaiCLI；通过领域化 RAG、降级、HITL 和可观测性形成差异化 |
| R-4 | MemoArk 资源冲突 | 中 | **冻结至 2027-03 后**；其 Obsidian/CSDN 素材未来可作 JobPilot 知识库语料 |
| R-5 | 刷题被项目挤压 | 高 | 11 月起项目开发 ≤10h/周，刷题并行线显式入里程碑 |
| R-6 | LLM API 成本失控 | 中 | 嵌入本地零成本；NFR-2 月度 ¥100 硬上限；Agent max_iterations = 5 |
| R-7 | 检索质量不达预期 | 中 | 评测集驱动调优；若连续调优 2 周 P@5 < 70%，先优化切分/阈值/降级，不提前更换向量库 |
| R-8 | M-2 Agent 核心 loop 延期 | 中 | 先保留 ≤300 行的小型同步 ReAct runner；若仍超时，砍长期记忆和复杂工具，保留基础对话 + knowledge_search |
| R-9 | 与 JRAG 简历口径混淆 | 低 | 明确区分：JobPilot = 原创自研 0→1；JRAG = 源码研读/复刻；PaiCLI = 通用引擎 |
| R-10 | AI 框架更迭焦虑 | 低 | 项目是常量、框架是变量；当前只评估 Spring AI，不为简历关键词迁移框架 |
| R-11 | 本地环境损坏 | 低 | NFR-4 每日备份；原始文档 + Chroma 目录 + MySQL 三件套可重建 |

## 13. 附录

### 13.1 个人面试准备目标（非产品验收标准）

> 以下为本项目的**能力成长目标**，不纳入产品验收，但指导架构决策取舍：

- 面试准备能力：能脱稿讲清自研 ReAct runner、工具协议、HITL/trace 和 RAG 检索取舍；
- 检索策略调优过程（评测集驱动）：能脱稿讲 ≥ 15 分钟；
- 框架选择：能解释为什么评估 Spring AI、为什么不把高层 Agent 控制流交给框架；
- 整体叙事：「通用引擎（PaiCLI）→ 领域落地（JobPilot）」能讲清

### 13.2 前端交互概要（指导 M-4 PRD 细化）

| 页面 | 核心能力 |
|---|---|
| 对话页 | ① 多轮对话 + SSE 流式输出；② 引用溯源标记可点击跳转原文；③ 输入区支持粘贴 JD / 上传文件快捷入口；④ 历史会话列表 |
| 知识库管理页 | ① 文档列表（名称/类型/切块数/导入时间）；② 上传入口（拖拽 + 粘贴）；③ 分块预览（查看某文档被切成哪些 chunk）；④ 删除文档（级联删 Chroma）；⑤ 重建索引（单文档/全量） |

### 13.3 文档导入格式处理规则

| 格式 | 处理方式 | 质量标准 | 失败兜底 |
|---|---|---|---|
| .md | 直接解析，按标题层级切分 | 保留标题结构作为 metadata | — |
| .txt | 按空行/固定长度切分 | — | — |
| .pdf（纯文本） | 通过轻量文本抽取器或待评估的 Spring AI/基础库适配 | 抽取后字符数 > 原文页字数 60% 视为合格 | 抽取质量低时提示用户手动粘贴 |
| .pdf（表格/扫描） | **不处理**（见非目标） | — | 用户手动复制粘贴为 txt/md |
