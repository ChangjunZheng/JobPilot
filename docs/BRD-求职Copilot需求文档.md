## 1. 背景与机会

- 求职是每年数以千万计的校招生、社招跳槽者与转行者必须经历的高强度信息处理过程：链条长（JD 筛选 → 匹配 → 面试准备 → 投递 → 复盘）、周期集中、且每一次求职的信息几乎无法沉淀复用。
- 跨人群的共性痛点：

  1. JD 散落在各招聘平台、内推群与聊天记录里，分析靠肉眼逐条比对；
  2. 简历与岗位的匹配度、差距清单全凭感觉，缺少可追溯的依据；
  3. 面试准备低效——八股与项目细节复习没有优先级，不知道该补哪；
  4. 投递进度散落在 Excel / 聊天记录，复盘无从谈起；
  5. 以上信息换岗位、换行业后从零重来，历史积累不产生复利。

- **私密性是本赛道的结构性机会**：简历、面经、投递记录属于高度敏感的个人信息，用户对「把这些交给第三方工具」存在天然戒备。这既是通用 AI 助手用几段 prompt 难以覆盖的信任缺口，也是 JobPilot 用「个人知识库 + 数据隔离 + 可删除可导出」建立差异化的基础。
- 市面 AI 工具竞品扫描：

  | 工具类型 | 代表 | 它们做了什么 | JobPilot 差异点 |
  |---|---|---|---|
  | AI 简历优化 | 超级简历、Kickresume | 单点"帮你写/改简历" | 全流程闭环 + 个人知识库 |
  | 面试模拟 | Pramp、Interviewing.io | 真人对练 / 固定题库 | 基于**用户自己项目经历**的 Agent 追问 |
  | 知识管理+AI | Notion AI、Obsidian Copilot | 通用文档问答 | 求职领域定制切分/检索/引用策略 |
  | 投递追踪 | 各类 Excel 模板、Notion 模板 | 手动表格记录 | 对话式记录 + 自动统计 + Agent 复盘 |
  | 招聘平台内置 | BOSS 直聘、LinkedIn | 岗位推荐、在线投递、进度状态 | 面向**求职者侧**的长期资产沉淀，不做投递引擎、不绑定单一平台 |

- 双重目标：
  - **产品目标**：为求职者提供可自助注册、可长期使用的求职流程工作台，替代散落的 Excel 与聊天记录；
  - **技术目标**：以可运行、可测试、可解释的工程实现支撑上述闭环（多租户隔离、RAG 检索质量、Agent 控制流、可观测性），不以堆砌框架数量作为亮点。

## 2. 目标用户

| 角色 | 定位 | 核心诉求 | 优先级 |
|---|---|---|---|
| 求职者（校招） | 主要用户 | 批量处理 JD、按优先级准备面试、管理投递进度 | P0 |
| 求职者（社招 / 转行） | 主要用户 | 用历史经历匹配新岗位、整理跨行业信息、弥补知识差距 | P0 |
| 高强度求职者（海投型） | 主要用户 | 高频投递记录、批量 JD 分析、阶段性复盘统计 | P1 |
| 平台运营 / 客服 | 内部角色 | 用户支持、异常排查、内容合规处置 | P1 |
| 机构管理员（高校就业中心 / 培训机构） | 远期场景 | 批量开通账号、组织级配额与统计 | P2，本期不做 |

- **多租户是本期的架构前提**：所有业务数据必须按用户隔离，注册登录是核心链路的一部分，不再是可选项。
- 本期唯一开户方式是求职者自助注册；机构批量开户（组织层级、成员管理、组织级数据视图）保留至 P2。

## 3. 产品目标（北极星）

> 一句话：把「JD → 匹配 → 准备 → 投递 → 复盘」全流程，装进一个带个人求职知识库的 Agent 对话台。

- **北极星指标**：周活跃用户中完成「导入个人材料 → 至少一次引用问答或 JD 分析」的比例（激活留存率）≥ 40%。
- 配套指标（初版目标，上线后按真实数据校准）：
  - 注册 → 完成首次文档导入的转化率 ≥ 60%；
  - 单用户周均有效会话数 ≥ 3；
  - 引用问答的引用点击率（用户点击溯源引用的比例）≥ 30%；
  - 投递记录模块的 4 周留存率 ≥ 50%。

> 上述数值为发布前设定的初始目标，不具备真实流量前不作为验收硬门槛；首个完整版本上线 4 周后按实际数据重新校准并写入本节。

## 4. 核心场景（用户故事）

| ID | 场景 | 级别 | 描述 | 验收条件 |
|---|---|---|---|---|
| US-6 | 注册与登录 | P0 | 求职者自助注册账号并登录，之后所有材料、对话与记录归属自己，对其他用户完全不可见 | ① 支持邮箱注册与登录（手机号可后置）；② 未认证请求无法访问任何业务接口；③ 跨账号访问他人数据一律拒绝并记录安全日志；④ 支持登出与凭证过期续期 |
| US-1 | 知识库问答 | P0 | 导入 JD/面经/八股/项目文档后提问，回答**引用溯源**到具体文档段落 | ① 支持 md/txt/PDF 导入；② 回答附带 [文档名 > 段落] 格式引用；③ 无相关内容时明确告知而非编造 |
| US-2 | JD 分析 | P0 | 粘贴 JD → Agent 解析技术栈/要求/疑点 → 结合用户简历给出匹配度与差距清单 | ① 输出结构化（技术栈/经验要求/疑点三段）；② 差距项可追溯到简历原文；③ 支持单 JD 对比 |
| US-3 | 面试模拟官 | P0 | 选岗位与范围 → Agent 多轮追问（基于用户的项目细节深挖）→ 评估报告 + 弱点清单写入长期记忆 | ① 至少 3 轮递进追问（基础→深挖→压力）；② 追问引用知识库中项目文档；③ 结束后生成弱点摘要并写入记忆 |
| US-4 | 投递进度管理 | P1 | 对话式记录/查询/统计投递状态（看板视图移 P2） | ① 自然语言记录投递（公司/岗位/状态/日期）；② 按状态/时间查询；③ 简单统计（总数/各状态数）；④ 看板视图 P2 |
| US-5 | 简历要点生成 | P1 | 基于 JD 与个人经历生成要点草稿，**HITL：AI 生成 → 人工确认后才入库** | ① 输入 JD + 选择目标经历；② 输出 3~5 条定制化要点；③ 用户逐条确认/编辑后才写入；④ 拒绝的草稿不持久化 |
| US-7 | 数据自管理与退出 | P1 | 用户随时查看、导出并删除自己的全部数据，包括注销账号 | ① 支持导出个人数据（文档/对话/记忆/投递记录）；② 支持注销账号并清除全部数据；③ 删除操作覆盖数据库、向量库与原始文件；④ 删除不可恢复且需二次确认 |

> 面向公众的 SaaS 中，US-6 与 US-7 不是加固项而是产品准入条件：前者决定能否对外提供服务，后者决定是否满足个人信息保护的合规底线。

## 5. 功能范围（P0/P1/P2 分级，保护关键路径）

| 级别 | 范围 | 说明 |
|---|---|---|
| **P0（核心闭环）** | **FP-9** 用户账号、鉴权与租户数据隔离；**FP-1** 文档导入 → 切块 → 嵌入 → 向量检索 + 引用问答；**FP-2** 最小同步 Agent（自研 ReAct runner + `knowledge_search` / JD 分析工具）；**FP-3** 基础 trace + 一个 HITL 审批场景；**FP-5** 模型配置（本地/云端双路径可切换） | 对外提供服务的最低标准。鉴权与租户隔离是 P0 而非加固项——没有它，产品不能对外开放 |
| **P1（产品化增强）** | **FP-4** 基础长期记忆；投递 CRUD 工具；**FP-10** 用量计量与配额；**FP-6** 最小前端（对话页 + 知识库管理页） | 只在 P0 稳定后实现。前端不属于「可后置的装饰」：面向公众的产品无法只交付 API |
| **P2（商业化与扩展）** | **FP-11** 订阅与计费；SSE 流式；组织与成员管理；多模型路由；复杂记忆治理；完整投递体验与数据导出自助化 | 时间或资源紧张时后置；保留为后续迭代项 |

### 5.1 实现依赖顺序

```
FP-9 账号体系与租户隔离（P0，所有业务能力的前置）
  └─► FP-1 RAG Pipeline
        └─► FP-2 Agent 对话 + 知识库检索工具（依赖 FP-1 提供检索接口）
              └─► FP-3 横切点 trace / HITL（叠加在 FP-2 的 Agent 循环上）
                    └─► FP-4 长期记忆（依赖 FP-2 工具注册机制 + FP-3 审批门控）
FP-5 LLM 配置（贯穿，FP-1 之前即需可用；含本地/云端路径切换）
FP-10 用量计量（叠加在 FP-2 / FP-5 上，按租户统计 token 与调用量）
FP-6 最小前端（在 FP-1 / FP-2 接口趋于稳定后并行开发，不作为后端闭环前置）
```

> FP-9 由 I-1 交付，FP-1 的既有实现需在此之前完成租户键的贯通校验；FP-2 → FP-3 → FP-4 按序递进，FP-5 随 FP-2 一起完成。

## 6. 非目标（明确不做）

- ❌ 简历复杂排版 / PDF 渲染（已有简历工具链）；
- ❌ **PDF 表格结构还原 / 扫描件 OCR**（求职材料以 md/txt 与网页复制为主，此类文件兜底 = 手动粘贴）；
- ❌ 爬虫抓取招聘平台（合规风险，JD 一律手动粘贴）；
- ❌ 通用 chatbot（一切功能围绕求职领域）；
- ❌ **招聘方 / HR 侧产品**（B 端简历筛选、候选人管理、面试排期）——JobPilot 只服务求职者一侧，不与用户的雇主产生利益冲突；
- ❌ 社交与社区功能（面经分享、互评、求职圈）；
- ❌ 机构多层级组织与权限体系（组织、部门、成员角色），保留至 P2；
- ❌ 自动投递 / 平台对接（合规 + 复杂度双重不可控）；
- ❌ **超大规模架构**：不做分库分表、多机房容灾、亿级向量检索。本期以单集群 + 明确容量上限（见 NFR-7）支撑早期用户规模，扩容触发条件写进 NFR 而不是提前设计。

> 「不做高并发/高可用」「不做多端同步」在 v0.5 中成立的前提是单用户自用，通用化后不再适用：多租户隔离、基础并发能力与数据合规已升级为必做项，见 §8 NFR-4 / NFR-5 / NFR-6。

## 7. 成功标准（可验证）

| ID | 标准 | 验证方式 |
|---|---|---|
| S-1 | 产品可对外注册并被真实求职者（本人以外）使用 | 上线后 4 周内：注册 → 首次导入转化率 ≥ 60%，且北极星激活留存率 ≥ 40% |
| S-2 | 面试模拟：对任一粘贴的 JD 能生成有层次的追问 | 演示 + 用户抽样：基础 → 项目深挖 → 压力面，至少 3 轮递进 |
| S-3 | 检索质量达标 | 20 条评测集 P@5 ≥ 80%（详见 §7.1） |
| S-4 | 全流程可用 | 10~20 个真实 JD 走通 JD→匹配→准备→投递→复盘 |
| S-5 | 租户隔离无泄漏 | 越权测试全通过：任何跨账号的读/写/检索请求均被拒绝并留痕；上线前完成一次隔离专项检查 |
| S-6 | 数据可退出 | 随机抽取账号执行导出 + 注销，确认数据库、向量库、原始文件三处数据全部清除 |

### 7.1 评测集规范

| 维度 | 说明 |
|---|---|
| 规模 | 20 条固定 QA 对（问题 + 期望引用段落 ID） |
| 类型分布 | 事实型 8 条（某技术点定义/用法）、比较型 5 条（A vs B 优劣）、综合型 4 条（跨文档关联）、无答案型 3 条（应拒答） |
| 判定标准 | P@5 = Top5 检索结果中命中期望段落的比率高；"命中" = 引用段落与期望段落**文本重叠 ≥ 50%** 或同属一段 |
| 触发时机 | I-1 交付时跑第一次；每次变更切分/嵌入/检索策略后重跑；I-4 全流程演练前终测 |

> 评测集基于固定语料（不得混入任何用户的真实私密材料），随代码入库；个人层面的能力目标移至 §13.1 附录。

## 8. 非功能需求（NFR）

| ID | 维度 | 要求 | 说明 |
|---|---|---|---|
| NFR-1 | 响应延迟 | 单次 RAG 检索（含嵌入）≤ 2s；首 token 输出 ≤ 5s；非 LLM 类 API P95 ≤ 3s | 在基准容量（NFR-7）下测量，不承诺跨地域延迟。**耗时随输入规模线性增长的操作（如文档索引）不得同步执行**——必须改为受理即返回、后台完成、状态可查，否则单请求可占用线程数分钟 |
| NFR-2 | 成本模型 | 嵌入与模型服务采「本地默认 + 云端可配」双路径：本地 Ollama 为零边际成本默认路径，云端 API 按 token 计量并按租户归集 | 单用户是有意义的成本归集单位（用于配额与后续定价）；不设个人月度上限，改为可配置的租户配额 |
| NFR-3 | 降级策略 | 云端 LLM 超时 → 重试 1 次后返回友好错误；向量库不可用 → 降级关键词检索并在响应中标记；嵌入服务不可用 → 停止新索引并提示。**降级必须对用户可见**，不得静默降级后仍宣称是语义检索 | 降级语义从「单机自用的容错」变为「面向不确定网络与第三方依赖的服务契约」 |
| NFR-4 | 多租户隔离 | 所有读写按租户强制过滤；跨租户访问返回 404/403 并写安全日志；向量库侧同样以租户键过滤；隔离由框架/数据访问层保证，不依赖每个调用点自觉传参 | **架构不变量**。任意一个漏掉的过滤条件都是数据泄漏事故 |
| NFR-5 | 身份与凭证安全 | 密码加盐哈希（不可逆）；凭证支持过期与续期；密钥与凭证不得进入代码、日志或 git | |
| NFR-6 | 数据合规与隐私 | 求职材料属个人信息，须明示收集范围与用途；提供数据导出与删除（含账号注销）；删除必须覆盖数据库、向量库与原始文件三处 | 面向公众产品的准入条件，非「以后再说」的加固项 |
| NFR-7 | 容量与扩展 | 单集群支持 ≤ 1000 活跃用户、单用户 ≤ 500 篇文档 / ≤ 200 万字；触达上限前先垂直扩容，不做分库分表 | 容量上限显式写死，便于判断何时必须做架构升级 |
| NFR-8 | 可观测性 | 每次 Agent 调用记录 trace（输入/工具链/输出/耗时/token/租户），写入日志表；trace 不得跨租户可见 | 支撑排障与成本归集 |
| NFR-9 | 可用性 | 目标可用性 99%（单集群 + 计划内维护窗口）；维护需提前公告 | 早期产品不做多机房容灾，但需要明确的可用性口径 |

## 9. 发布迭代（产品节奏）

迭代不绑定日历日期。每个迭代开始前给出预估周期，结束后按实际节奏滚动调整下一迭代的排期。

> **本节只定义「要交付什么」，不记录「做到哪了」。** 进度状态、任务级清单、当前阻塞与已知缺陷见 [`ROADMAP.md`](./ROADMAP.md)——那是进度状态的唯一事实来源。

| 迭代 | 主题 | 产出 | 出口条件 |
|---|---|---|---|
| **I-0** | 技术基线与 RAG 最小闭环（**已完成**） | Spring Boot 4.0 / Spring AI 2.0.1 接入；导入 → 嵌入 → 向量库 → 引用问答的最小 API 闭环 | 已达成（实现见 `src/main/java` 与 PRD） |
| **I-1** | 账号体系与租户隔离 | 注册登录、凭证管理、租户键贯通所有业务表与向量库 metadata、越权防护 | 新用户可独立注册并完成导入 → 引用问答；跨租户越权用例全通过（S-5） |
| **I-2** | Agent 最小闭环 | 自研同步 ReAct runner + `knowledge_search` + JD 分析工具 + trace + 一个 HITL 场景 | 工具调用、迭代上限、超时重试、审批幂等均可演示 |
| **I-3** | 长期记忆与投递管理 | Memory 写入/审批链路 + 投递 CRUD 与统计工具 + 用量计量 | 记忆与投递数据全链路租户隔离；用量可按租户归集 |
| **I-4** | 产品化外壳 | 最小前端（对话页 + 知识库管理页）、注册登录页、空态与错误态打磨 | 目标用户可无文档自助完成核心流程；10~20 个真实 JD 端到端演练通过 |
| **I-5** | 商业化与合规收口 | 配额、订阅与计费、数据导出与账号注销自助化、SSE 流式输出 | 具备对外收费与个人信息合规要求的完整能力 |

- **回退准则**：若某迭代的核心能力在预估周期 1.5 倍时间内仍未跑通，触发范围重审——把该迭代的非核心项顺延至下一迭代，保住 P0 闭环完整，不允许为了保住日期而砍掉租户隔离或 HITL 这类安全边界。
- **I-1 的优先级高于一切功能迭代**：在多租户隔离落地前，不对外开放注册，也不接受真实用户的私密材料。

## 10. 技术基线（约束级，细化留给架构设计）

- 后端：Java 21 + Spring Boot 4.0 + MyBatis-Plus 3.5.x + MySQL + Redis；
- AI：Spring AI 2.0.1 作为基础接入层（已在 I-0 落地），统一 Chat/Embedding/Tool Calling 的供应商协议；业务层只依赖 JobPilot 自定义 Port/record，**不引入 LangChain4j 作为运行时依赖**，Agent 控制流（ReAct 循环、预算、HITL、trace）由 JobPilot 自研，不交给框架。**LangGraph4j 已评估暂缓**——它是库不是框架、也不强迫引入 LangChain4j，暂缓理由是「图编排 + checkpointing」与线性 ReAct 循环不匹配（详见 `docs/ARCHITECTURE.md` §1.4.1）；
- 嵌入与生成：**「本地默认 + 云端可配」双路径**——本地 Ollama（`bge-m3` 嵌入）为零边际成本默认路径；云端 embedding / LLM API 作为可配置的可选路径。两条路径对业务层不可见，由 Port 与配置项隔离；
- 向量库：Chroma 为默认本地实现；`VectorStorePort` 抽象须允许替换为托管向量库，以支撑云端部署形态。**不引入 Elasticsearch 替代向量检索**；
- 多租户：所有业务表带租户归属键，向量库侧以 metadata 过滤；鉴权使用无状态凭证（JWT 或等价方案），身份边界集中在适配层，业务服务不得到处写死用户标识；
- 流式：SSE 后置（I-5 及以后），先完成同步闭环；
- 前端：**不作为后端闭环的前置依赖，但属于产品可交付的必要组成**——面向公众的 SaaS 不能只交付 API，最小前端在接口稳定后启动（I-4）；
- 模型与循环策略：模型名称、endpoint、超时、`max_iterations` 全部配置化；Agent 循环默认 `max_iterations = 5` 防无限递归；
- 密钥管理：所有第三方凭证通过环境变量/密钥管理注入，不得进入代码库与日志。

## 11. 核心概念模型（BRD 级，指导架构设计方向）

### 11.1 关键实体关系

```
User (1) ──── (1) Credential          # 账号凭证
User (1) ──── (N) Document
User (1) ──── (N) Conversation ──── (N) Message
User (1) ──── (N) Memory (长期记忆条目)
User (1) ──── (N) Application (投递记录)
User (1) ──── (N) UsageRecord (用量计量)
User (1) ──── (N) ApprovalDraft (审批草稿)
Document (1) ──── (N) Chunk ──── (1:1) VectorEntry (向量库)
Conversation (N) ──── (1) JobDescription? (可选关联)
```

| 实体 | 存储 | 说明 |
|---|---|---|
| User | MySQL | 账号主体，**同时是本期唯一的租户单元** |
| Credential | MySQL | 登录凭证（邮箱 + 加盐哈希），与 User 一对一 |
| Document | MySQL 元信息 + 向量库 | 原始文件副本保留在存储目录；切块后 Chunk 文本存 MySQL，向量存向量库 |
| Conversation / Message | MySQL | 多轮对话记录，支持按时间/关联 JD 查询 |
| Memory | MySQL 自建表 | 用户级持久知识（见 §11.2） |
| Application | MySQL | 投递进度（公司/岗位/状态/时间/关联 JD/备注） |
| UsageRecord | MySQL | 按租户归集的 token / 调用量，支撑配额与成本核算 |
| ApprovalDraft | MySQL | 待用户确认的副作用候选 |
| TraceLog | MySQL | Agent 调用链路日志（见 NFR-8） |

> **租户模型**：本期租户 = 用户个人（`user_id` 即租户键），不引入组织层级。模型上保留未来升级为「组织 → 成员」两级的空间，但**不提前实现组织表、角色表与成员邀请机制**（见 §6 非目标）。
>
> **不要把它读成「RBAC 延后」**：租户内只有一个用户，没有权限可分配，本项目**根本不使用 RBAC**。多租户（数据隔离）与 RBAC（授权）是两个正交的轴——隔离、认证、授权三轴的分工与演进见 `docs/ARCHITECTURE.md` §1.7.1。计划新增的 FP-9 只覆盖前两轴。

### 11.2 长期记忆 vs RAG 知识库边界

| 维度 | RAG 知识库（Document/Chunk） | 长期记忆（Memory） |
|---|---|---|
| **内容** | 外部导入文档：JD、面经、八股、项目描述 | Agent 交互中**自动/半自动沉淀**的结构化条目 |
| **粒度** | 文档级 / 段落级 | 单条知识/偏好级（如"Java 并发方面表达不自信"） |
| **生命周期** | 用户主动增删改 | Agent 面试评估后写入弱点；用户可显式删除/编辑；不自动过期 |
| **使用方式** | 检索增强——召回段落注入 prompt 作为参考依据 | 记忆注入——作为 system prompt 上下文，影响 Agent 行为策略 |
| **举例** | "Spring 事务传播机制详解" 文档段落 | "用户在分布式事务场景被追问 2 次未答好" |

> 设计原则：记忆条目 **短小、可枚举、结构化**（JSON/表格行）；知识库内容 **长文本、需向量检索**。如果一条信息 > 200 字或需要语义检索，它应该进知识库而非记忆。
>
> **隔离前提**：知识库与长期记忆同为租户私密数据，检索、注入、导出、删除四条路径都必须带租户约束。**记忆注入进 system prompt 时尤其危险**——一次漏过滤就等于把他人隐私拼进了当前用户的对话上下文。

### 11.3 HITL 审批流程

触发条件：Agent 产生**对外持久化副作用**时，必须经用户确认后才执行：

| 操作 | 审批粒度 | 拒绝处理 |
|---|---|---|
| US-5 简历要点写入知识库 | 逐条确认（可编辑后确认） | 丢弃该条草稿，不持久化 |
| US-3 面试弱点写入长期记忆 | 整批确认（评估报告一次性审核） | 可选择部分条目写入 |
| 知识库文档删除 | 单次确认 | 取消删除 |
| 投递记录写入/更新 | 自动执行（低风险，无需审批） | — |
| US-7 账号注销（用户主动发起，非 Agent 产物） | 二次确认 + 影响明示 | 取消注销，数据保持不变 |

> 不触发审批的操作：纯检索、对话回复、trace 日志写入、JD 解析输出（仅展示，不持久化）。
>
> **多租户下 HITL 的额外约束**：审批草稿本身也是租户数据，只对发起者可见；审批动作必须校验操作者与草稿归属者一致，防止通过构造草稿 ID 替他人执行副作用。

## 12. 风险与对策

| ID | 风险 | 影响 | 对策 |
|---|---|---|---|
| R-1 | 范围蔓延（做成八爪鱼） | 高 | 严格 P0/P1/P2；新想法一律先进 backlog，不进当前迭代 |
| R-2 | **多租户数据泄漏** | 极高 | 隔离作为架构不变量（NFR-4），由数据访问层强制注入租户条件，不在业务代码里手工传参；上线前执行越权专项测试（S-5）；向量库侧同样过滤 |
| R-3 | **个人信息合规风险** | 高 | 明示收集范围与用途、最小化采集、支持导出与删除（NFR-6 / US-7）；上线前完成一次合规自检；不采集与求职无关的敏感信息 |
| R-4 | 嵌入/LLM 成本随用户量增长 | 中 | 双路径策略（NFR-2）：默认本地嵌入零边际成本；云端路径按租户计量并设配额；Agent 设 `max_iterations` 与 max tokens 上限 |
| R-5 | **冷启动无用户** | 高 | 早期以本人 + 少量种子用户 dogfooding 验证激活指标；指标先看「注册 → 首次导入 → 激活留存」漏斗，再看规模；不提前为不存在的大流量做架构 |
| R-6 | 滥用与恶意注册（刷量、爬取） | 中 | 注册风控、按租户限流与配额、异常行为审计；不采集与业务无关的个人信息以降低被撞库价值 |
| R-7 | 检索质量不达预期 | 中 | 评测集驱动调优；若连续调优 2 周 P@5 < 70%，先优化切分/阈值/降级，不提前更换向量库 |
| R-8 | Agent 核心 loop 延期 | 中 | 保留 ≤300 行的小型同步 ReAct runner；若仍超时，砍长期记忆和复杂工具，保留基础对话 + `knowledge_search` |
| R-9 | **前端交付持续后置导致产品不可交付** | 中 | 前端在 I-4 作为独立迭代项排期，不参与后端压缩；若前端延期，API 只能内部使用，不得对外宣称产品可用 |
| R-10 | 与参考项目（PaiCLI / PaiSmart）叙事重叠 | 中 | JobPilot 不直接复用其业务代码；通过领域化 RAG、降级策略、HITL 和多租户隔离形成差异化 |
| R-11 | AI 框架更迭焦虑 | 低 | 项目是常量、框架是变量；已落地 Spring AI 2.0.1，后续升级由真实适配收益驱动，不为框架关键词迁移 |
| R-12 | 基础设施故障与数据丢失 | 中 | MySQL 定期备份 + 原始文件与向量库可重建；备份与恢复说明必须可执行，不伪装成应用功能 |
| R-13 | 第三方模型/API 供应商变更或涨价 | 中 | 双路径 + Port 抽象：本地路径可兜底，云端供应商可替换，不把控制流绑定在单一供应商的 SDK 上 |

## 13. 附录

### 13.1 技术能力目标（非产品验收标准）

> 以下为本项目的**工程能力沉淀目标**，不纳入产品验收，但指导架构决策取舍：

- 框架选择：能解释为什么选 Spring AI 而非 LangChain4j 或高层 Agent 框架，以及为什么 Agent 控制流不交给框架；
- 本地 / 云端双路径的 Port 抽象如何做到对业务层透明。
