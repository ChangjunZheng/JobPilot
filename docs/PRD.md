## 1. 产品概述

### 1.1 产品目标

JobPilot 将以下流程集中到一个带个人知识库的 Agent 工作台：

```text
JD / 个人材料导入
    → 知识库检索与引用问答
    → JD 分析与匹配
    → 面试准备与模拟追问
    → 投递记录
    → 复盘与弱点沉淀
```

产品同时服务两个目标：

1. **实际提效**：减少手工比对、零散记录和无优先级复习。
2. **能力证明**：展示 Java 21、RAG、Agent、工具调用、HITL 和可观测性工程能力。

### 1.2 目标用户

| 用户 | 当前版本定位 | 需求 |
|---|---|---|
| 个人求职者（本人） | 唯一实际用户 | 管理个人材料、准备面试、追踪投递和复盘 |
| 同届同学 | 未验证假设，不纳入本期验收 | 未来可能复用，但不提前建设完整多用户产品 |

### 1.3 产品原则

- **领域优先**：所有 Agent 能力围绕求职，不做通用 chatbot。
- **证据优先**：涉及个人经历和知识库的问题尽量给出原文引用；无依据时明确说明未知。
- **人工掌控副作用**：会写入知识库或长期记忆的 AI 产物必须经过用户确认。
- **先同步后流式**：先完成可测试的同步闭环，再叠加 SSE。
- **评测驱动**：检索质量以固定评测集衡量，不以主观演示替代。
- **轻量工程**：单用户、低并发，不为未来不确定的多用户场景过度设计。

### 2.2 明确不在本期

以下内容保留在 P2 backlog，不得以“顺手实现”的方式进入本期验收：

- JWT 注册、登录和完整权限系统；
- 多模型路由、自动模型选择；
- 招聘平台爬虫、平台对接和自动投递；
- PDF 表格结构还原、扫描件 OCR、PDF 渲染和复杂简历排版；
- 投递看板、移动端、实时协同和多端同步；
- 求职周报、导出、上下文摘要治理；
- 高并发、高可用、分布式向量库和亿级数据容量设计。

## 3. 角色、前置条件与身份边界

### 3.1 角色

本期只有一个角色：**求职者用户**。

用户可以：

- 导入、查看、删除自己的文档；
- 查询和使用自己的知识库；
- 发起对话、JD 分析和模拟面试；
- 查看、创建和更新自己的投递记录；
- 审批 AI 生成的持久化草稿；
- 查看自己的记忆和 Agent trace 摘要。

### 3.2 身份处理

- 所有持久化业务对象从 day1 保留 `user_id`。
- JWT 登录属于 P2，本期不提供注册登录页面。
- 开发/单用户模式由应用上下文提供固定开发用户标识；该适配方式必须集中在身份边界，业务服务不得到处写死用户 ID。
- 任意查询、修改和删除操作都必须按 `user_id` 做数据隔离，即使当前只有一个用户。

### 3.3 前置条件

完整 AI 闭环需要以下外部服务：

| AI 接入层 | 当前 M-1 为 JobPilot 自定义 Port + `RestClient` 适配 Ollama/Chroma；M-2 评估 Spring AI | 不把 LangChain4j 作为当前运行时依赖；Spring AI 只负责基础模型/工具协议适配，不接管 Agent 控制流 |
| MySQL | 元数据、文本、会话、记忆、投递、trace | M-2 前按实际功能接入 |
| Chroma | Chunk 向量存储与相似度检索 | M-1 已接入 |
| Ollama + `bge-m3` | 本地文本嵌入 | M-1 已接入 |
| LLM API / Ollama Chat | 对话、分析、生成 | M-2 前配置化 |
| Redis | 会话/缓存等基础能力 | 不作为 P0 核心闭环前置依赖 |

## 4. 核心用户流程

### 4.1 文档导入与索引

```text
用户选择文件或粘贴文本
    → 校验格式与大小
    → 创建文档记录（PENDING）
    → 提取文本
    → 切分并生成 Chunk
    → 调用本地 embedding
    → 写入 Chroma 与 Chunk 元数据
    → 文档状态 READY
```

失败时进入 `FAILED`，保留失败原因和可重试入口；不得把未完成索引的文档当作可检索内容。

### 4.2 知识库问答

```text
用户提出问题
    → 检索 Top-K Chunk
    → 判断是否达到相关性阈值
    → 组装带引用上下文
    → 生成回答
    → 返回回答、引用和 trace 摘要
```

无相关内容时返回明确的“当前知识库没有足够依据”，不得使用无引用的确定性措辞编造个人经历。

### 4.3 JD 分析

```text
用户粘贴一份 JD
    → 解析岗位信息、技术栈、经验要求和疑点
    → 检索个人简历/项目材料
    → 生成匹配度、优势、差距和建议
    → 展示原文引用
```

JD 分析结果默认只展示，不自动写入长期记忆或知识库；用户主动保存时再进入后续审批/持久化流程。

### 4.4 模拟面试

```text
用户选择岗位或输入 JD、选择主题
    → Agent 提出基础问题
    → 用户回答
    → Agent 基于项目材料递进追问
    → 至少完成基础、深挖、压力三轮
    → 生成评估报告与弱点候选
    → 用户整批确认或部分确认
    → 确认项写入 Memory
```

拒绝或未确认的弱点候选不得写入长期记忆。

### 4.5 投递记录

```text
用户自然语言表达投递信息或使用记录入口
    → 提取公司、岗位、状态、日期等字段
    → 展示解析结果
    → 写入或更新 Application
```

投递记录属于低风险业务写入，按 BRD 规则无需 HITL；字段不完整时先要求补充，不得猜测关键字段。

### 4.6 简历要点生成

```text
用户选择 JD 与个人经历
    → Agent 生成 3~5 条草稿
    → 用户逐条编辑、确认或拒绝
    → 仅确认项写入目标知识库
```

生成阶段不得产生持久化副作用；拒绝的草稿不保存。

## 5. 功能需求

### 5.1 FP-1 文档导入与 RAG 检索（P0）

#### PRD-FP-1.1 文档接收

**输入：** 文件上传或文本粘贴，附带可选标题、文档类型和标签。

**支持格式：**

| 格式 | 处理 | 规则 |
|---|---|---|
| Markdown | 支持 | 保留标题层级作为 Chunk metadata |
| Plain text | 支持 | 按空行和固定长度切分 |
| PDF 纯文本 | 有条件支持 | 仅抽取文本，不保证表格结构 |
| PDF 扫描件/复杂表格 | 不支持 | 提示用户复制为 md/txt 后重新导入 |

**业务规则：**

- 原始文件副本保留在配置的本地数据目录；文件路径不得直接作为跨用户可见信息返回。
- 文档必须归属一个 `user_id`。
- 同一文档是否允许重复导入由后续架构设计决定；本期至少要避免一次操作产生不可追踪的重复索引。
- 导入请求成功只代表任务已创建，不代表索引完成；状态必须可查询。

**验收：**

- md/txt 能进入索引流程并最终成为可检索文档。
- 不支持的 PDF 能返回可理解的失败原因和替代建议。
- 空文件、无法读取或提取文本为空时进入 `FAILED`，不写入空 Chunk。

#### PRD-FP-1.2 切分与索引

每个 Chunk 至少保留以下业务信息：

- `document_id`、`chunk_id`；
- 原文文本；
- 顺序号、标题/章节路径；
- 起止位置或可复现的引用定位信息；
- `user_id`；
- 创建时间和索引版本。

切分要求：

- md 优先按标题层级切分，再对过长章节进行长度切分；
- txt 按段落和长度切分；
- 保留适度重叠，具体 chunk size/overlap 在评测集上确定；
- 修改切分策略或 embedding 模型时必须支持重建索引；
- 索引写入应具备可重试性，避免重复写入导致引用重复或脏数据。

#### PRD-FP-1.3 相似度检索

**输入：** `user_id`、自然语言查询、可选文档类型/标签过滤、Top-K（默认 5）。

**输出：** 按相关性排序的 Chunk 列表，包括文本、文档名称、章节路径、相关性分数和引用定位。

**规则：**

- 检索只能命中当前用户的数据；
- 低于相关性阈值的结果不应强行注入回答；
- Chroma 不可用时按 NFR-3 降级为 MySQL 关键词检索，并明确标记结果为降级结果；
- Ollama 不可用时停止新索引任务，向用户提示嵌入服务离线。

#### PRD-FP-1.4 引用问答

回答必须能够将依据映射到：

```text
[文档名 > 章节/段落]
```

验收要求：

- 正常问题返回回答和至少一个可定位引用（若知识库存在足够相关内容）；
- 无答案问题返回明确拒答或信息不足提示；
- 引用文本必须来自实际检索 Chunk，不允许由模型虚构文档名或章节；
- 单次 RAG 检索（包括嵌入）目标 ≤ 2 秒，作为 NFR-1 评测指标。

### 5.2 FP-2 Agent 对话与求职工具（P0，M-2）

#### 技术路线

- 首版使用 JobPilot 自研的最小同步 ReAct runner，控制最大轮次、工具预算、超时、异常回填和终止条件。
- Spring AI 是候选基础接入层：如果能减少 Chat/Embedding/Tool Calling 的供应商适配代码，可以引入；但不让高层 Agent 抽象接管 JobPilot 的 ReAct、HITL 和 trace。
- 不引入 LangChain4j 作为当前运行时依赖；不直接复制 PaiCLI/PaiSmart 的业务实现。
- 目标不是自研通用 Agent 框架，而是实现一个**能被面试官追问、范围可控的领域 Agent**。

#### 求职时间紧张时的最小范围

**必须做：**

1. 无工具调用时能直接回答；
2. `knowledge_search` 工具能被调用并回填结果；
3. 一个 JD 分析工具能跑通；
4. 最大迭代次数、工具异常、LLM 超时可控；
5. 每轮 trace 能记录模型、工具、耗时和状态；
6. 一个写入类工具实现 `PENDING_APPROVAL` 和幂等审批。

**可以后置：**

- 多 Agent 计划/执行/审查；
- 上下文自动摘要；
- 工具并行执行；
- 完整投递 CRUD 和统计；
- SSE、WebSocket、完整前端；
- 多模型路由和复杂长期记忆。


#### PRD-FP-2.1 对话上下文

对话由 `Conversation` 和有序 `Message` 组成。每条消息至少具有：

- `conversation_id`、`user_id`；
- 角色：`USER`、`ASSISTANT`、必要时 `TOOL`；
- 文本内容；
- 创建时间；
- 可选关联 `job_description_id`；
- 可选引用列表和 trace 标识。

本期不要求上下文摘要治理；上下文过长时允许提示用户开启新会话或按模型限制截断，并记录可观测信息。

#### PRD-FP-2.2 工具注册

Agent 至少支持以下工具：

| 工具 | 作用 | 副作用 |
|---|---|---|
| `knowledge_search` | 检索用户知识库 | 无 |
| `job_description_analyze` | 解析 JD 并结合个人材料形成分析 | 默认无 |
| `application_create` | 创建投递记录 | 低风险写入，无需审批 |
| `application_update` | 更新投递记录 | 低风险写入，无需审批 |
| `application_query` | 查询投递记录 | 无 |
| `application_stats` | 按状态/时间统计 | 无 |
| `memory_candidate_create` | 生成长期记忆候选 | 必须进入 HITL |

工具调用必须有最大迭代次数，默认 `5`；达到上限时返回当前已获得结果和可理解的中止说明。

#### PRD-FP-2.3 JD 分析输出

分析结果至少包含：

1. 岗位基本信息：公司、岗位名称、地点/工作模式（若 JD 提供）；
2. 技术栈与能力要求；
3. 经验/学历/实习要求；
4. 岗位疑点或需要进一步确认的内容；
5. 与个人材料的匹配度（说明评分依据）；
6. 优势清单；
7. 差距清单；
8. 每个关键差距对应的个人材料引用或“未找到依据”。

模型无法确定的字段必须标记为未知，不得补全为事实。

### 5.3 FP-3 Trace 与 HITL（P0）

#### PRD-FP-3.1 Trace

每次 Agent 调用至少记录：

- `trace_id`、`user_id`、`conversation_id`；
- 开始/结束时间、总耗时；
- 输入摘要（敏感内容按后续安全策略脱敏）；
- 使用的模型配置；
- 工具调用顺序、参数摘要和结果状态；
- 输出状态、错误类型；
- token 消耗（外部模型能够提供时）。

Trace 用于排查和演示，不作为用户知识库内容参与检索。

#### PRD-FP-3.2 审批门控

| 操作 | 审批方式 | 确认后动作 | 拒绝后动作 |
|---|---|---|---|
| 简历要点写入 | 逐条 | 写入确认项 | 丢弃该条 |
| 面试弱点写入 Memory | 整批，可部分选择 | 写入选中项 | 未选中项不写入 |
| 知识库文档删除 | 单次确认 | 删除元数据、原文件和向量 | 保持不变 |
| 投递记录写入/更新 | 不审批 | 直接写入 | 校验失败时要求补充 |

审批草稿必须有明确状态，例如 `PENDING`、`APPROVED`、`PARTIALLY_APPROVED`、`REJECTED`、`EXPIRED`。过期或已处理的草稿不得重复执行副作用。

### 5.4 FP-4 长期记忆（P0）

Memory 用于保存短小、结构化、用户级的偏好或弱点，不替代 RAG 文档库。

**允许内容：**

- 求职偏好；
- 面试弱点；
- 已确认的准备计划或表达问题。

**不允许直接写入：**

- 未经确认的模型猜测；
- 长篇文档或需要语义检索的材料；
- 其他用户数据。

每条记忆至少包括：`memory_id`、`user_id`、类型、内容、来源（如面试评估）、置信/说明字段、状态、创建/更新时间。用户可以查看、编辑和删除自己的记忆。

### 5.5 FP-5 LLM 模型配置（P0）

本期以配置项级切换为目标，不做多模型路由。至少支持：

- 模型名称；
- API endpoint；
- API key（仅环境变量/安全配置注入）；
- temperature；
- max tokens；
- Agent `max_iterations`，默认 5；
- 超时和重试次数。

默认开发模型为 `deepseek-chat` 或等价低成本模型。模型调用超时超过 30 秒时重试一次，仍失败则返回友好错误并记录 trace；不得无限重试。

### 5.6 FP-6 对话页与知识库管理页（P1）

#### 对话页

必须支持：

- 新建/切换/查看历史会话；
- 输入问题、粘贴 JD；
- 查看回答、工具调用结果摘要和引用；
- 查看加载中、错误、重试状态；
- M-4 叠加 SSE 流式输出，先保证同步回答可用。

#### 知识库管理页

必须支持：

- 文档列表：名称、类型、状态、Chunk 数、导入时间、失败原因；
- 上传或粘贴导入；
- 查看文档 Chunk 预览与引用定位；
- 删除文档（确认后级联删除索引）；
- 单文档/全量重建索引；
- 空知识库和索引失败的明确提示。

看板视图、复杂编辑器和移动端不在本期。

### 5.7 FP-7 投递进度完整体验（P1）

`Application` 至少包含：

- 公司；
- 岗位名称；
- 状态；
- 投递日期；
- 来源/链接（可选）；
- 关联 JD（可选）；
- 备注；
- `user_id`、创建/更新时间。

状态枚举首版建议为：`WISHLIST`、`APPLIED`、`SCREENING`、`INTERVIEWING`、`OFFER`、`REJECTED`、`WITHDRAWN`。新增状态需同步更新统计和验收用例。

完整体验支持按状态、时间范围查询，以及总数和各状态数量统计；不要求看板拖拽。

### 5.8 FP-8 简历要点生成（P1）

输入为一份 JD 和用户选择的个人经历/文档。输出 3~5 条草稿，每条包含：

- 要点文本；
- 对应经历依据；
- 与 JD 要求的关联；
- 用户可编辑文本。

只有用户确认的条目才可写入知识库。系统必须能区分“生成成功”和“已持久化”；拒绝或关闭页面不应产生写入。

## 6. 业务状态与数据契约

### 6.1 Document 状态

```text
PENDING → PROCESSING → READY
                    └→ FAILED → PROCESSING（重试）
READY → DELETING → DELETED
```

`DELETED` 数据不可继续出现在检索结果；删除向量失败时必须记录不一致状态并提供重建/清理入口。

### 6.2 核心业务对象

| 对象 | 必备业务含义 | 关键关系 |
|---|---|---|
| Document | 用户导入的原始材料 | 1:N Chunk |
| Chunk | 可引用、可检索的文本片段 | 归属 Document；对应 Chroma vector entry |
| Conversation | 一次连续对话 | 1:N Message |
| Message | 用户/助手/工具消息 | 可关联引用和 trace |
| JobDescription | 可选的结构化 JD | 可关联 Conversation/Application |
| Memory | 已确认的用户级短条目 | 归属 User |
| Application | 一条投递记录 | 可关联 JobDescription |
| TraceLog | 一次 Agent 调用链路 | 关联 Conversation |
| ApprovalDraft | 待用户确认的副作用候选 | 关联来源操作和用户 |

### 6.3 引用契约

引用是回答的一部分，不是只存在日志中的调试信息。每个引用至少需要：

- `document_id`、展示名称；
- `chunk_id`；
- 章节/段落定位；
- 引用文本或可安全展示的摘要；
- 与回答的关联顺序。

引用定位必须能够从知识库管理页跳转到对应原文或 Chunk 预览。

## 7. 异常、空状态与降级

| 场景 | 用户可见行为 | 数据行为 |
|---|---|---|
| 知识库为空 | 提示先导入文档 | 不调用无意义的回答生成 |
| 无相关 Chunk | 提示没有足够依据 | 允许记录对话，不生成伪引用 |
| Ollama 不可用 | 提示“嵌入服务离线，请检查本地服务” | 新索引失败，可重试 |
| Chroma 不可用 | 提示正在使用关键词检索/服务暂不可用 | 允许降级查询，标记 trace；不能静默伪装为向量检索 |
| MySQL 不可用 | 显示服务暂不可用 | 不确认写入成功，不丢弃客户端可重试请求 |
| LLM 超时 | 重试一次后显示友好错误 | 记录失败 trace，不无限重试 |
| 文件格式不支持 | 告知支持格式和替代方式 | 创建失败记录或不创建业务文档，行为需一致 |
| 文档索引失败 | 显示失败原因和重试入口 | 文档为 `FAILED`，不参与检索 |
| Agent 达到迭代上限 | 返回已完成部分并提示中止 | 记录工具链和上限原因 |
| 审批草稿过期/重复提交 | 阻止重复副作用并提示当前状态 | 保持幂等 |

所有失败状态都应可关联 `trace_id` 或操作 ID，便于排查。

## 8. 非功能需求与验收口径

| ID | 产品验收口径 |
|---|---|
| NFR-1 | 普通请求首 token 目标 ≤ 5 秒；单次 RAG 检索含嵌入 ≤ 2 秒。在固定本地环境和测试数据集上记录 P50/P95。 |
| NFR-2 | 月度 LLM API 成本 ≤ ¥100；embedding 默认使用本地 Ollama；单次 Agent 最大迭代 5 次并设置 max tokens。 |
| NFR-3 | Ollama、Chroma、LLM API 的不可用行为符合第 7 节；每种降级至少有一个自动化或手工验收用例。 |
| NFR-4 | MySQL、原始文件、Chroma 数据目录均有可执行的备份/恢复说明；本期不把备份脚本伪装成应用功能。 |
| NFR-5 | 支持 ≤500 篇文档、≤200 万字的预期容量；不要求分布式扩展。 |
| NFR-6 | 每次 Agent 调用有完整 trace：输入/工具链/输出状态/耗时/模型/可用 token 信息。 |

数据安全要求：API key、数据库密码和 Redis 密码不得进入代码、日志或 git；用户数据查询必须带 `user_id`；原始文件路径不得直接暴露给前端。

## 9. 验收标准

### 9.1 功能验收清单

- [ ] md/txt 文档可导入、切分、索引、检索和删除。
- [ ] 纯文本 PDF 可按质量规则处理；扫描件/复杂表格被明确拒绝。
- [ ] 知识库问答能返回实际引用；无答案时不编造。
- [ ] JD 分析包含技术栈、要求、疑点、匹配度、优势和差距，并能引用个人材料。
- [ ] Agent 至少能调用知识库检索和 JD 分析工具，最大迭代次数生效。
- [ ] 模拟面试可完成基础→深挖→压力至少三轮。
- [ ] 面试弱点和简历要点必须经过相应 HITL 后才写入。
- [ ] 投递记录支持创建、更新、查询和统计，字段按 `user_id` 隔离。
- [ ] Trace 可追踪模型、工具链、耗时和错误。
- [ ] P1 对话页和知识库管理页覆盖空、处理中、成功、失败和重试状态。
- [ ] P1 SSE 在同步闭环稳定后接入，断流时有错误提示，不影响已完成内容。

### 9.2 检索评测集

建立 20 条固定 QA 对，每条包含问题、期望引用段落 ID 和类型：

| 类型 | 数量 | 要求 |
|---|---:|---|
| 事实型 | 8 | 命中技术定义/用法段落 |
| 比较型 | 5 | 命中比较双方或关键依据 |
| 综合型 | 4 | 命中跨文档关联依据 |
| 无答案型 | 3 | 正确拒答或说明证据不足 |

- `P@5` 目标 ≥ 80%。
- 命中定义为引用段落与期望段落文本重叠 ≥ 50%，或属于同一明确段落。
- M-1 交付、每次改变切分/embedding/检索策略后、M-4 演练前各执行一次。
- 无答案型不能只看检索命中率，还要验证最终回答没有伪造事实。

### 9.3 端到端演练

M-4 前使用 10~20 个真实 JD 完成：

```text
导入材料 → 粘贴 JD → 分析匹配 → 面试准备 → 记录投递 → 查看统计 → 复盘弱点
```

每个 JD 至少记录：流程是否走通、人工介入点、错误、耗时、引用质量和需要 hotfix 的问题。

## 11. 依赖与实施顺序

```text
FP-1 RAG Pipeline
  └─► FP-2 Agent + knowledge_search / JD 分析
        └─► FP-3 trace / HITL
              └─► FP-4 长期记忆
FP-5 LLM 配置贯穿以上流程
FP-6/7/8 产品壳在同步闭环稳定后于 M-4 交付
```

- JobPilot 自研最小同步 ReAct runner 是 M-2 的默认实现，不把 PaiCLI `agent-kernel` 复用设为前置条件。
- Spring AI 只作为候选基础 AI 接入层；若引入，业务层仍只依赖 JobPilot 自定义 Port/record，Agent 控制流仍由 JobPilot 控制。
- SSE 不得成为同步闭环的前置依赖。

## 12. 待架构设计确认项

以下事项不阻塞本 PRD，但必须在架构设计阶段落定：

1. Spring AI 是否能在不接管 Agent 控制流的前提下减少 Chat/Embedding/Tool Calling 适配代码。
2. Chroma API 版本、collection 命名、删除/重建索引和一致性策略。
3. chunk size、overlap、embedding 维度和相似度阈值，以评测集结果决定。
4. 原始文件目录、文件命名、防路径穿越和备份/恢复策略。
5. MySQL 表拆分、索引、软删除与 Document/Chunk/VectorEntry 一致性。
6. Redis 是否用于会话、幂等键或缓存，避免无明确收益的引入。
7. 固定开发用户身份如何在未来切换到 JWT，而不改业务服务接口。
8. SSE 断线恢复、重复事件和已生成内容的持久化策略。
9. trace 中输入/输出的脱敏规则和日志保留周期。
10. 前端具体技术栈；BRD 建议 Vue 3 + Element Plus，但不作为本 PRD 的实现硬约束。

## 14. 假设与版本记录

### 14.1 当前假设

- 当前产品由单个求职者 dogfooding，暂不需要邀请、共享或管理员角色。
