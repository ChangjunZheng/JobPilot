# 写交接记录

**目的**：让另一个窗口（或明天的自己）能接上——它读不到你的上下文，只能读这个文件。

**产出**：`docs/学习/交接/YYYY-MM-DD.md` 里属于**本窗口**的那一段。

---

## 第一步：判断今天是什么日期、文件在不在

```bash
ls "docs/学习/交接/$(date +%Y-%m-%d).md"
```

- **不存在** → 从 `docs/学习/交接/TEMPLATE.md` 复制一份，重命名为当天日期
- **已存在** → **只改本窗口的那一段，绝不覆盖另一个窗口的内容**

> ⚠️ **最容易犯的错：用 Write 整个覆盖文件**。当天文件里可能有另一个窗口刚写的内容。
> 已存在时一律用 Edit 追加/替换本段。

## 第二步：确定自己是哪个窗口

- **开发窗口**（写代码、跑测试、提交）→ 写「开发窗口」段
- **学习窗口**（`/guided-learning` 激活中）→ 写「学习窗口」段

拿不准就问用户，别猜。

## 第三步：收集事实，别凭记忆写

**开发窗口——先确认本次是否形成了可交接的开发里程碑。** 用户手动调用本 skill 时，默认是在一个功能或一轮开发收尾；不要把所有零碎编辑堆成流水账。

用 git 和测试结果说话：

```bash
git log --oneline --since="今天 00:00"          # 今天提交了什么
git diff --stat HEAD~N..HEAD                    # 改了哪些文件
git status --short                              # 未提交的改动
```

并确认：

- **代码冻结点**：学习窗口应基于哪个 commit / 当前提交状态阅读；如果还有未提交改动，明确写出，不能把它说成已冻结；
- **测试证据**：实际跑了哪些命令、结果如何、哪些测试没有跑；不要只写"测试通过"；
- **开发里程碑**：本次交付了什么功能，是否只是中间步骤；
- **推荐学习点**：从本次变更中挑 **1~3 个最值得学习的核心设计**，说明为什么挑它们，
  并指明**教材来源**（本项目 / `github_repos` / 官方文档 / `Code_Test`）；
  同时写出"本次不需要学什么"；不要把所有变更都变成学习任务；
- **已知缺口**：还有什么未完成、风险或下一步。

**学习窗口**——从对话里提取：讲了哪几节、用户在哪里卡住、下次讲什么，以及三层能力变化：

- **已能复述**：能说出代码做了什么；
- **已能解释**：能说出为什么这样设计；
- **已能判断**：换一个场景时能否选择类似方案。

> **不要编造**。不确定的细节就写"待确认"，或者问用户。

## 第四步：写。开发窗口必须写「改了哪些模块」和「推荐学习点」

**这是开发窗口最该写的两节**——学习窗口靠它们确定教材范围，而不是追逐整个项目。

### 开发窗口段的必填项

**1. 本次交付**：一句话说清完成了哪个开发里程碑。

**2. 代码冻结点**：写 commit hash 和工作区状态：

```text
代码冻结点：d76aaaf；工作区干净
```

如果有未提交改动，必须写：

```text
代码冻结点：无；仍有未提交改动：...
```

**3. 测试证据**：写实际命令和结果：

```text
测试证据：`mvn test -Dtest=AccountServiceTest,PasswordHasherTest`，通过
未运行：完整 `mvn test`（需要本机 MySQL）
```

**4. 改了哪些模块**：学习窗口靠这一节判断**已讲过的内容是否失效**。

| 模块 | 改了什么 | 对已讲内容的影响 |
|---|---|---|
| `KnowledgeRetrievalService` | catch 结构新增 `UnauthorizedException` 分支 | 第 3 节失效 |

**5. 推荐学习点（1~3 个）+ 去哪学**：只挑最有设计价值的内容，并指明教材来源：

| 学习点 | 为什么值得学 | 主教材 | 通用对照 |
|---|---|---|---|
| 时间侧信道的哑哈希 | 统一错误文案挡不住耗时差 | `PasswordHasher` / `AccountService` | `D:\Workspace\github_repos` 里找同类认证实现 |

**教材来源可选值**：

- **本项目**（`src/main/java/...`）——项目取舍、真实落地；
- **开源项目**（`D:\Workspace\github_repos`）——通用机制的成熟实现；
- **官方文档**；
- **`D:\Workspace\Code_Test`**——需要动手实验 / 复现故障时。

**为什么要写"去哪学"**：通用机制在优秀开源项目里往往更清楚、更成熟，JobPilot 只回答
"我为什么这样做"。不写清楚，学习窗口会把批次时间全花在项目代码上。

**同时写出"本次不需要学什么"**（样板代码、DTO、Controller 转发之类），避免学习范围失控。

**不要把整个 diff 变成学习清单。** 学习窗口一次只消化 1~3 个核心设计，达到"能复述 / 能解释 / 能判断"后就算完成本批次。

**6. 已知缺口 / 下一步**：测试没补、风险、后续里程碑。

**只写"完成 X 功能"是不够的**：如果重构了 `KnowledgeRetrievalService`，学习窗口讲过的那一节就过时了，但它无从得知。

**学习窗口的「卡在哪」写的是学习缺口，不是代码缺陷**——加一句提醒，免得开发窗口误当待修项。

## 各节要点

| 节 | 怎么写 |
|---|---|
| 本次交付 | 一句话说清交付的开发里程碑 |
| 代码冻结点 | **commit hash + 工作区是否干净**；未提交改动必须明示 |
| 测试证据 | **实际命令 + 结果 + 未运行什么**，不要只写"测试通过" |
| 改了哪些模块 | **开发窗口必填**，见上 |
| 推荐学习点 | **开发窗口必填，1~3 个**；说明为什么值得学、**去哪学**（本项目 / `github_repos` / 官方文档 / `Code_Test`），并写明本次不需要学什么 |
| 卡在哪 / 已知缺口 | **具体**：粘贴真实报错 > 描述现象。不要写"有点问题" |
| 为什么这么选 | **最值钱的一节**（也是面试素材）：选了什么 / 否掉了什么 / 代价是什么 |
| 学到的东西 | 学习窗口填；写三层能力变化，不只写看过哪些文件 |
| 下次继续 | 小到"打开就能干"；开发窗口写下一里程碑，学习窗口写下一学习批次 |

**档位那两行**（文件顶部）是学习窗口的启动参数，水准判断跨不了会话——**学习窗口写交接时必须更新它**，并引用具体哪次作答作为判据。

## 第五步：写完报告

告诉用户：写到了哪个文件、哪一段、**本次新增了什么**。如果发现另一个窗口的段有内容，确认没被覆盖。

---

## 边界

- **只写交接文件**，不改代码、不动 `精华/`。
- `精华/` 是另一个东西——见 `~/.claude/skills/guided-learning/references/workflow.md` §3.1。
  它**不是**交接的副本，是剥掉时间性、展开重写的成品。用户说"归档/提炼精华"时别走这个 skill。
- `docs/学习/` 已 gitignore，**不要提交**。
- 短就是好。五行能说清就别写十行。
